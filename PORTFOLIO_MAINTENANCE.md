# Pragalbh.in — Maintenance Contract

Updated: 26 August 2026

This portfolio is a living evidence system. It should grow when Pragalbh's work produces new evidence, not whenever another technology name looks attractive.

## 1. What triggers a portfolio update

Update the portfolio when one of these occurs:

- a meaningful project reaches a new maturity stage
- a public repository becomes substantial enough to demonstrate capability
- a prototype becomes a pilot or deployment
- a field problem produces a useful troubleshooting case
- an institutional process becomes repeatable/documented
- a real outcome becomes measurable
- a new capability is repeatedly applied, not merely studied
- a role/responsibility materially changes

Do not update the live portfolio for every experiment, one-off command or tool trial.

## 2. Required update sequence

For new work:

`work → evidence → proof classification → outcome classification → case update → capability link → release audit`

Never reverse the order by writing a strong portfolio claim first and looking for evidence afterward.

## 3. Project maturity states

Use explicit states:

- **Concept / exploration** — useful thinking, insufficient applied proof
- **Source-backed architecture** — formal requirements/design evidence exists
- **Prototype** — implementation exists but is not an operational rollout
- **Pilot** — used in a limited real setting
- **Applied / field work** — real operational implementation/troubleshooting occurred
- **Live system** — publicly or operationally active
- **Continuous improvement** — operating system with ongoing iteration

Only move a case forward when evidence supports the change.

## 4. Skill maturity states

Use the existing hierarchy rather than calling everything expert:

- Core strength
- Strong
- Applied
- Developing / growing
- Prototype architecture
- Field troubleshooting
- Exploring

A skill becomes more prominent when multiple projects connect to it.

## 5. Flagship promotion rules

A supporting case can become flagship when it has most of these:

- meaningful problem/constraint
- clear Pragalbh role
- non-trivial architecture/decision-making
- evidence beyond prose
- trade-offs or failure modes
- operational relevance
- credible current state
- useful outcome or learning
- connection to several capability branches

Maintain a small flagship set. Adding a seventh flagship should usually require demoting or merging another one.

## 6. Evidence-media rules

Preferred hierarchy:

1. live public system
2. public repository
3. privacy-safe real screenshot
4. privacy-safe field photograph
5. source-backed derivative architecture diagram
6. redacted process/document example

Do not use generic stock photography as evidence.

For every media file record:

- case study
- claim proven
- source type
- privacy status
- caption
- alt text
- date captured where useful

Store under `assets/media/<case>/` using descriptive names.

## 7. Outcome rules

Consult `OUTCOME_REGISTER.md` before publishing impact.

Good outcome evidence includes:

- measured deployment/rebuild time
- restore/recovery test result
- manual-step reduction
- publishing turnaround
- fault-resolution evidence
- real edge power consumption/autonomy
- pilot workflow feedback
- application/workflow completion data

Do not reconstruct impressive metrics from memory months later.

## 10. Monthly maintenance review

A lightweight monthly review should check:

- broken external links
- stale project statuses
- repository links still relevant
- live systems still reachable
- new public evidence worth adding
- outcome opportunities worth measuring
- old supporting cases that can be removed/merged
- skills that now have stronger evidence
- privacy/attribution drift
- GitHub audit workflow health

Do not redesign the site monthly. Maintain the evidence.

## 11. Quarterly portfolio review

Every quarter:

- review the five-pillar positioning
- review flagship hierarchy
- review recruiter opportunity paths
- review leadership/technical balance
- check whether current professional direction has changed
- retire low-signal content
- add only evidence-backed new work
- perform real device/browser QA
- record any material roadmap changes

## 12. When new field photos become available

Before upload:

1. identify the case
2. crop away irrelevant details
3. redact sensitive screens/labels/IDs
4. remove embedded location metadata if appropriate
5. convert to WebP/AVIF
6. create mobile-friendly size
7. write factual caption/alt text
8. add it to the evidence register
9. run `npm run audit`

## 13. When a new GitHub repository becomes portfolio-worthy

Evaluate:

- does it show a capability not already proven better elsewhere?
- does the README explain the system clearly?
- is the repository safe to make prominent?
- are credentials/internal topology absent?
- is the project state explicit?
- is there a meaningful decision story?

If yes, add it as evidence first. Promote to a case study only if the story justifies the space.

## 14. Change-control principle

The portfolio's default state should remain sparse.

When adding information, prefer:

- deeper nodes
- evidence inside existing cases
- related-capability links
- collapsed supporting content

Avoid adding another permanent homepage section unless the information cannot be represented through the existing network, recruiter view or case-study model.

## 15. Definition of healthy maintenance

The portfolio is healthy when:

- claims stay current
- evidence gets stronger over time
- page length does not creep upward
- the network becomes richer without becoming noisier
- the recruiter path stays fast
- project maturity remains honest
- privacy and attribution boundaries hold
- CI stays green
- new work naturally maps into the evidence system

The website is not the product. The evidence model is the product; the interface is how people inspect it.
